# Runbook — applying migration `20260723221731_security_hardening.sql`

**Status:** staged, NOT applied to prod. This runbook is WP-SEC-11's deliverable;
its stage gates are the binding ones from Ascension Plan §4 amendment 12.
**The runbook applies nothing itself. Stages 1, 3, and 4 are owner-executed.**

## Why this migration is urgent

The migration's lineage revoked `program_orders` (and 7 other tables) from the
`authenticated` role, and several live routes (`bundles/download`,
`user/dashboard-summary`, the bundle detail ownership gate) already assume the
post-migration state — they read those tables through the **service** client
only. Until the migration is applied, prod schema and code disagree: the
Data API surface the code no longer uses is still exposed.

## What it does (5 blocks)

1. **Profile field protection** — trigger `protect_profile_managed_fields`
   blocks a user session from editing 17 server-managed columns on its own
   `profiles` row (role, streaks, tjxp, credit balance, …). Service-role
   writes are unaffected.
2. **Wallet provisioning + atomic redemption** — wallet-per-user trigger +
   backfill; `redeem_tjfit_discount` becomes atomic (wallet row lock),
   idempotency-keyed, and executable by `service_role` only.
3. **Coach upload cap under concurrency** — advisory-lock trigger enforcing
   the 3-active-programs cap per coach.
4. **Storage buckets** — upserts `community-blog-images` (public) and
   `program-assets` (private, PDF-only).
5. **Data API revoke** — revokes `anon`/`authenticated` grants on 8 tables
   served only through scoped Next.js APIs (`program_orders`,
   `tjfit_coin_wallets`, `tjfit_coin_ledger`, `tjfit_discount_offers`,
   `tjfit_discount_codes`, `custom_programs`, `marketing_subscribers`,
   `community_blog_posts`).

## Stage sequence (amendment-12 gates — each stage has a hard pass/fail)

### Stage 1 — branch apply (owner-run)

Create a Supabase preview branch of project `kohuiyqyixvrcqeepalz` and apply
the migration to it (Dashboard → Branches, or `supabase db push` against the
branch).

**PASS:** the migration runs to completion with **zero errors** (warnings on
`drop … if exists` of absent objects are fine).
**FAIL:** any statement errors → stop, file the error verbatim, do not
proceed. The migration was written idempotently (`if not exists` /
`drop if exists` / upserts), so a clean re-run after a fix is safe.

### Stage 2 — e2e on the branch

Point a local checkout at the branch (branch env vars in `.env.local`) with
`ALLOW_TEST_CHECKOUT=1` set **on the branch env only** — never prod (the
boot tripwire from WP-SEC-06 will refuse a prod boot with it set anyway).

Run both simulated money paths via the admin test routes:

1. `POST /api/admin/test/simulate-program-purchase` for a $10 bundle, then
   fetch the bundle download.
   **PASS:** download endpoint returns the PDF (HTTP 200, non-empty body)
   for the purchasing test user.
2. `POST /api/admin/test/simulate-credit-purchase`, then read the credit
   balance (dashboard summary or `consume-credit` probe).
   **PASS:** balance incremented by exactly the simulated pack size.

**FAIL:** either flow errors or the entitlement/balance doesn't materialize —
that means a route still depends on a pre-migration grant. Stop and file.

### Stage 3 — security advisor (owner-run)

Run the Supabase security advisor on the branch (Dashboard → Advisors).

**PASS:** zero **new** CRITICAL or HIGH findings relative to the advisor run
on main/prod before branching (pre-existing findings don't block — they're
tracked separately by WP-DATABASE-08).
**FAIL:** any new CRITICAL/HIGH → stop, attach the advisor output to the
plan doc, fix on the branch first.

### Stage 4 — prod apply (owner-run)

Apply the migration to prod (SQL editor paste or `supabase db push`),
ideally in a low-traffic window. The migration is transactional per
statement and idempotent; a mid-way failure can be re-run after the cause
is fixed.

**PASS:** same criterion as stage 1 — zero errors.

### Stage 5 — post-apply smoke (owner or agent)

```bash
npx tsx scripts/security/post-migration-smoke.ts
```

with prod env vars set (`NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`). The script is
**read-only** — it never writes, and its one RPC probe is expected to be
rejected at the permission layer.

**PASS:** script exits 0 —
- anon SELECT on all 8 revoked tables is hard-denied (error, not empty-200),
- service-role SELECT still works,
- `redeem_tjfit_discount` rejects anon callers at the grant (not in-body),
- both buckets exist with the right visibility,
- wallets table is backfilled (non-empty wherever users exist).

Then run the standard live check:

```bash
./scripts/verify-deploy.sh
```

**PASS:** verify-deploy.sh exits 0 against https://tjfit.org.

**FAIL on either:** treat as an incident — the revoke may have over-reached a
route the e2e didn't cover. `git log supabase/migrations` + the
`payment_webhooks` table are the first places to look; the revoke block can
be reverted table-by-table with explicit `grant select … to authenticated`
statements while diagnosing (document anything you re-grant).

## Rollback notes

- Blocks 1–3 (triggers/functions): `drop trigger` / `drop function` restores
  pre-migration behavior; no data change to undo (the wallet backfill is
  additive and harmless to keep).
- Block 4 (buckets): leave in place — other shipped code
  (SOCIAL-03 transformations, blog images) expects them.
- Block 5 (revokes): reversible per-table with `grant` statements; only
  re-grant a table if a concrete route regression traces to it.
