# TJAI v1 operations

The new purchase grants one initial plan, one successful regeneration per Europe/Istanbul calendar month, five successfully persisted replies per Europe/Istanbul calendar day, and ongoing access to saved plans, PDFs and logs. Initial generation does not consume regeneration. Existing purchase records and credits are retained. Active legacy Pro/Apex and administrators retain their chat access; old one-time plan owners use the five-reply allowance.

Historical generation rights deliberately preserve the baseline backend at commit `ac8dcba`: its generate route bypassed credits for old one-time purchasers, administrators and Pro/Apex, explicitly describing unlimited subscription generations. The older access/UI helper restricted the regeneration button more narrowly; this conflict is not used to remove existing backend entitlements. The new pass alone never qualifies as legacy. Legacy eligibility is checked at enqueue, before model execution and under row locks at final persistence; removal/cancellation of one source prevents completion unless another qualifying historical source survives. Current subscription statuses are `active` or `trialing`.

## Required configuration and deployment

Apply the reviewed Lemon commerce migration before the three TJAI migrations, in filename order. These migrations depend on existing canonical profiles, saved plans, subscriptions, credit functions, chat and workout tables. Intake and generated-plan writes belong to the server; users can read only their own rows. Logs retain owner CRUD policies.

The only model endpoint is Groq inference with `openai/gpt-oss-120b`. Sending intake/context requires `TJAI_PROVIDER_ENABLED=true`, `TJAI_GROQ_ZDR_CONFIRMED=true`, the matching account's inference Zero Data Retention setting, and `TJAI_LLM_API_KEY`. If set, the preset must be `groq`. No paid provider, alternate model, TTS or enrichment fallback is used. Optional coach-review and email benefits are not included.

Generation also requires the root-owned worker configuration: enablement, a 32–512 character internal secret and an HTTPS origin. Checkout and enqueue fail closed when it is absent. Immediate dispatch has a three-second bound; a failed dispatch leaves a persisted job for the five-minute recovery schedule. Deploy and verify both the background function and recovery schedule before accepting purchases. Configuration checks do not prove deployed worker or provider availability.

## Persistence and capacity behavior

The database reserves a legacy credit once when enqueuing its job. A successful result and plan version are persisted in one transaction. Failed terminal jobs refund that credit once, including expired worker leases. Pass entitlements are rechecked before model execution and locked/rechecked before final persistence. A refund during execution prevents new result delivery. Existing saved results remain readable.

Workers claim one job with a 120-second lease; recovery permits at most three attempts. Transient overload is queued with bounded backoff. The shared admission budget reserves a conservative UTF-8 upper bound plus output allowance: at most 7,000 tokens per UTC minute and 180,000 per UTC day. Failed provider requests still occupy this capacity. Provider errors never consume a successful reply or regeneration allowance. No automatic paid fallback exists.

## Product scope

The public assessment starts at `/{locale}/ai?tab=my-plan&start=1`; private hub tabs, owned intake links and sign-in resume links retain authentication. Completed validated answers and both consents remain in the original tab's session storage for up to two hours while the user signs in. The authenticated resume page asks explicitly to save, then opens the owned intake review. Completed temporary data is removed after a successful server save. Email verification opened in another tab does not transfer that draft; five-language verification and missing-draft messages direct users back to the original tab. No intake answers appear in return URLs.

Signup and verification resend use `/{locale}/auth/callback?next=...`. The callback exchanges the PKCE code using the original browser's verifier cookie and writes the session before redirecting to a validated same-locale page. Missing, expired or invalid codes return a localized verification failure with a safe sign-in target; no codes or provider errors are logged. Redirects are private/no-store and no-referrer. The installed Supabase browser client can also auto-exchange codes, but the prior homepage return did not resume the intended path. Production acceptance must verify Supabase allows the five deployed callback paths and the confirmation template honors the requested redirect URL. This code assumes the existing PKCE confirmation link; it does not change email templates or add token-hash/OTP confirmation. Same-browser/device verification remains a PKCE requirement, and opening a new tab does not transfer assessment session storage. See the [official PKCE flow](https://supabase.com/docs/guides/auth/sessions/pkce-flow) and [redirect configuration](https://supabase.com/docs/guides/auth/redirect-urls).

The intake is restricted to adults seeking general fitness. Unsupported clinical conditions, arbitrary injury/allergy restriction notes and underweight targets are rejected before payment. Supported catalog dietary exclusions are deterministic. Generation chooses only approved exercise and food IDs, then code calculates portions and expands a repeated weekly template with progression/deload blocks. This is not 84 unique daily menus. Food values and planned-meal log shortcuts are explicitly estimates; absent logs remain unknown. Strength summaries use actual per-set loads and volume.

Portions use a bounded deterministic solver, not calorie-only scaling. Each meal is limited to 750 g total food, 400 g combined protein foods, 20 g olive oil and the individual cooked/dry food bounds in `macro-balance.ts`. Generated calories and each daily macro must stay within 5% of their targets. The solver first tries the model's allowed pairing, then supplements or adjusts it using only permitted foods. Explicit accepted plant-protein sources are respected. Intake and both payment steps preflight feasibility; historical jobs recheck before calling Groq. Infeasible targets or catalog restrictions fail without a successful-generation allowance. These are approximate food values, not brand-specific nutrition labels or clinical diets.

Five UI languages and Unicode PDF fonts are supported. Bundle PDF headings are localized; existing deeper bundle descriptions and some exercise terms remain English. The 50 bundle-export smoke checks file generation, font glyph coverage and existing sections. It does not establish full editorial translation or physical print acceptance.

## Local verification

`npx vitest run tests/tjai-macro-balance.test.ts tests/tjai-durable-v1.test.ts tests/tjai-provider-policy.test.ts tests/tjai-generate-refund.test.ts tests/bundle-pdf-builder.test.ts tests/lemon-bundle-delivery.test.ts`

`node tests/tjai-database.integration.mjs <path-to-temporary-pglite-module>` executes the actual three migrations against an isolated PostgreSQL/WASM database with canonical fixture tables. It covers idempotency, lease loss and expiry, failed-credit refunds, month/day limits, refund-before-finalization, reserved reply tokens, distributed capacity and authenticated owner policies. It is not a production test or a multi-connection concurrency proof.

`node tests/tjai-postgres-concurrency.integration.mjs <temporary-runtime-directory>` uses the Windows binaries and `pg` client installed by `embedded-postgres` in that temporary directory. It creates a hidden, loopback-only PostgreSQL process and 12 independent connections, applies the same three migrations, and tests concurrent job deduplication/claim/refund, reply and provider admission limits, both refund/finalization lock orderings, a cross-owner reply-ID insertion race, and legacy purchase removal during finalization. The latest run passed 34 assertions on PostgreSQL 18.4. The test stops its own cluster and never creates a persistent service or connects to production.

`npx tsx scripts/tjai-pdf-smoke.ts <output-directory>` and `npx tsx scripts/bundle-pdf-smoke.ts <output-directory>` generate synthetic TJAI PDFs and all 50 enriched paid-bundle exports. Fonts are embedded from existing local assets by `scripts/build-tjai-pdf-fonts.py`.

Before live acceptance, verify database availability and migrations, authenticated account isolation, intake/payment/webhook return, queued recovery after a killed worker, successful Groq generation/chat, saved PDF download, failed/refunded purchase behavior, and all five locale flows. No local test substitutes for these deployment checks.
